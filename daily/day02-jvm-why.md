# JVM 위에서 실행된다는 것

## 1. 핵심 개념: 바이트코드와 JVM

- Java 소스는 컴파일해도 기계어가 나오지 않습니다. **바이트코드(.class)**가 나옵니다.
- 바이트코드는 OS가 직접 실행하지 않습니다. **JVM(Java Virtual Machine)**이 읽고 실행합니다.
- 이 한 단계(JVM)가 끼어드는 구조 때문에 워밍업, GC, Stop-the-World가 존재합니다.

> **JVM이 "어떻게" 실행되는지 모르면 흔한 증상 세 가지의 원인을 추론할 수 없습니다.** 배포 직후 5분간 느리다가 정상으로 돌아오는 현상, GC 때문에 수백 밀리초씩 멈추는 현상, Docker 이미지를 Alpine으로 바꿨더니 JNI 라이브러리가 깨지는 현상 — 전부 JVM 구조를 알아야 설명됩니다.

## 2. 구조

- **클래스로더**: `.class` 파일을 메모리에 올리고 JVM 명세에 맞는지 검증합니다.
- **인터프리터**: 바이트코드를 한 줄씩 해석해 실행합니다. 시작은 빠르지만 실행 속도는 느립니다.
- **JIT(Just-In-Time) 컴파일러**: 자주 실행되는 경로(핫 경로)를 감지해 기계어로 컴파일하고 캐시합니다. 시간이 지날수록 빨라집니다.

### 2-1. 선택적 확장 지점

- 기본 동작은 인터프리터로 시작해서 핫 경로를 계층적으로(C1 → C2) 최적화하는 **계층 컴파일(Tiered Compilation)**입니다.
- `-XX:TieredStopAtLevel=1` 옵션을 주면 C1까지만 쓰고 최고 수준(C2) 최적화는 포기하는 대신, 컴파일 단계 자체를 줄여 워밍업을 앞당길 수 있습니다. 짧게 실행되고 끝나는 프로세스에서 선택적으로 씁니다.

## 3. 흐름

### 3-1. 컴파일부터 실행까지

C/C++는 컴파일하면 특정 OS·CPU 아키텍처용 기계어가 나와서, macOS ARM용 바이너리는 Linux x86에서 돌아가지 않습니다. Java는 컴파일 결과물(바이트코드)과 실행 환경(JVM) 사이에 한 단계가 더 있습니다.

### 3-2. 실행 파이프라인

```
.java 소스 → .class 바이트코드 → 클래스로더 (로드·검증·링크)
클래스로더 이후 두 경로로 나뉘어 실행됨:
  ├─ 인터프리터   — 즉시 실행(느림)              → 기계어 실행
  └─ JIT 컴파일러 — 핫 경로를 기계어로 컴파일 → 기계어 실행
```

## 4. 특징

### 4-1. 이 특성이 두드러지는 상황

- AWS Lambda처럼 인스턴스가 짧게 사는 환경 — 항상 워밍업 단계에만 머무릅니다.
- 컨테이너 메모리 리밋을 빡빡하게 잡은 환경 — JVM 자체 오버헤드가 눈에 띕니다.
- JNI로 네이티브 라이브러리를 쓰는 순간 — 플랫폼 독립성이 깨집니다.

### 4-2. 장점

- **플랫폼 독립성**: `javac`로 한 번 컴파일한 `.class` 파일은 JVM이 있는 곳이라면 어디서든 실행됩니다.
- **자동 메모리 관리(GC)**: `malloc`/`free`를 직접 호출하지 않아도 됩니다.
- **런타임 최적화**: JIT는 실행 중 실제 사용 패턴을 보고 최적화합니다. 컴파일 시점에는 알 수 없는 정보입니다.

### 4-3. 단점 / 트레이드오프

- **워밍업 지연**: JIT가 핫 경로를 파악하고 컴파일하는 데 시간이 걸립니다. 배포 직후 느린 건 버그가 아니라 정상 동작입니다.
- **Stop-the-World**: GC가 힙을 정리할 때 모든 스레드가 잠시 멈춥니다.
- **메모리 오버헤드**: JVM 자체, JIT 코드 캐시, 클래스 메타데이터가 추가 메모리를 씁니다.

## 5. 예제: 워밍업을 대비하는가

### 5-1. 클린하지 않은 코드 ❌

```java
// ❌ 애플리케이션이 뜨자마자 바로 트래픽을 받는다
// JIT가 핫 경로를 아직 컴파일하지 못해 초기 요청들이 인터프리터 속도로 처리된다
```

### 5-2. 워밍업 러너를 적용한 코드 ✔️

```java
@Component
public class WarmupRunner implements ApplicationRunner {

    private final OrderService orderService;

    @Override
    public void run(ApplicationArguments args) {
        // 핫 경로를 미리 반복 호출해 JIT 컴파일을 앞당긴다
        for (int i = 0; i < 10_000; i++) {
            orderService.calculateDiscount(SAMPLE_ORDER);
        }
    }
}
```

- 트래픽을 받기 전에 핵심 경로를 미리 실행해두면, 실제 사용자 요청이 워밍업 비용을 떠안지 않습니다.

## 6. Write Once, Run Anywhere 원칙

- JVM이 존재하는 이유 자체가 이 원칙입니다: 한 번 컴파일하면 어디서든 실행됩니다.

### 6-1. 원칙이 깨지는 코드 ❌

```java
// ❌ JNI로 네이티브 라이브러리를 직접 로드 — 이 순간 OS·CPU 아키텍처에 종속된다
System.loadLibrary("native-image-processor"); // .so(Linux) / .dll(Windows)마다 따로 준비해야 함
```

- Alpine Linux(musl libc)와 Ubuntu(glibc)에서 같은 `.so` 파일이 호환되지 않는 이유가 여기 있습니다.

### 6-2. 원칙을 지킨 코드 ✔️

```java
// ✅ 순수 Java 라이브러리 사용 — JVM이 있는 곳이면 어디서든 동일하게 동작
BufferedImage resized = Thumbnails.of(source).size(200, 200).asBufferedImage();
```

## 7. 확장 지점 응용하기 — 컴파일 단계 조정

### 7-1. 클린하지 않은 코드 ❌

```bash
# ❌ 기본 설정 — 매번 짧게 실행되고 종료되는 환경에서는 C2까지 도달할 일이 거의 없다
java -jar app.jar
```

### 7-2. TieredStopAtLevel을 적용한 코드 ✔️

```bash
# ✅ C1까지만 사용 — 컴파일 단계를 줄여 초기 응답을 앞당긴다
java -XX:TieredStopAtLevel=1 -jar app.jar
```

- 실행 시간이 짧아 C2 수준 최적화에 도달할 일이 없는 프로세스라면, 컴파일 단계 자체를 줄이는 게 더 유리합니다.

## 8. 실무에서 찾아보는 JVM 시작 시간 단축 기법

- **CDS(Class Data Sharing)**: 클래스 메타데이터를 미리 파싱해 아카이브로 저장하고, 다음 실행부터 재사용해 클래스로딩 시간을 줄입니다. `-Xshare:on`으로 켭니다.
- **GraalVM Native Image**: 바이트코드를 빌드 시점에 미리 기계어로 컴파일(AOT)합니다. JIT 워밍업이 아예 없어 시작이 빠르지만, 런타임 최적화는 포기합니다.

## 9. 관련된 개념과 비교

### 9-1. JIT VS AOT 컴파일

**유사점**

- 둘 다 결국 바이트코드를 기계어로 바꿉니다.

**차이점**

- JIT는 런타임에, 실제 실행 패턴을 관찰하며 컴파일합니다. 워밍업이 필요하지만 실행 중 정보로 더 최적화할 수 있습니다.
- AOT(GraalVM Native Image)는 빌드 시점에 미리 컴파일합니다. 워밍업이 없어 시작이 빠르지만, 런타임에만 알 수 있는 정보로는 최적화하지 못합니다.

## 10. 함정

**배포 직후 느린 걸 장애로 오인해 롤백한다**

- **증상**: 배포 직후 몇 분간 응답이 느리다가 저절로 정상으로 돌아옵니다.
- **원인**: JIT가 아직 핫 경로를 컴파일하지 못해 인터프리터 속도로 실행 중입니다.
- **해법**: 배포 직후 알람 임계값에 워밍업 시간을 감안하거나, 트래픽을 받기 전에 워밍업 러너를 실행합니다. (5장 참고)

**컨테이너 메모리 리밋 전부를 힙으로 잡는다**

- **증상**: 힙 사용량은 리밋보다 한참 낮아 보이는데 컨테이너가 OOMKilled 됩니다.
- **원인**: 메타스페이스, 코드 캐시, 스레드 스택 등 JVM 자체 오버헤드가 힙 밖에서 추가로 메모리를 씁니다. 힙을 리밋 전부로 잡으면 이 오버헤드가 들어갈 자리가 없습니다.
- **해법**: 힙 크기를 컨테이너 메모리 리밋보다 여유 있게 설정합니다. 정확한 오버헤드 비율은 애플리케이션마다 달라 직접 측정이 필요합니다.
