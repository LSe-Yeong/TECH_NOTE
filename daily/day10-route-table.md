# public/private 서브넷의 실체는 라우팅 테이블입니다

> 이 문서가 답할 질문: **서브넷이 퍼블릭인지 프라이빗인지는 무엇이 결정하고, 라우팅 테이블은 패킷의 목적지를 어떤 순서로 고르는가?**
>
> 기준: Amazon VPC 사용자 가이드 (2026년 8월 확인). `day04-vpc-subnet.md`에서 "왜 나누는가"를 다뤘다면, 이 문서는 "나눈 것이 실제로 무엇으로 구현되는가"를 다룹니다.

## 1. 핵심 개념

VPC에는 **암묵적 라우터(implicit router)** 가 하나 있습니다. 서브넷을 떠나는 모든 패킷은 이 라우터를 거치고, 라우터는 **그 서브넷에 연결된 라우팅 테이블**을 보고 어디로 보낼지 정합니다. 라우팅 테이블은 규칙(route)의 목록이고, 규칙 하나는 **목적지(destination)와 타깃(target)** 두 칸이 전부입니다.

> 콘솔에서 서브넷을 만들어 보면 "Public / Private"을 고르는 필드가 없습니다. 없는 게 정상입니다. **퍼블릭 서브넷이라는 리소스 타입은 존재하지 않습니다.** 그 서브넷에 연결된 라우팅 테이블에 `0.0.0.0/0 → igw-xxx` 한 줄이 있으면 퍼블릭이고, 없으면 프라이빗입니다. 이걸 모르면 "분명히 프라이빗 서브넷에 DB를 넣었는데 왜 인터넷에서 접근이 되지"를 영원히 못 풉니다. 서브넷 이름을 `private-db`로 지어도 라우팅 테이블이 IGW를 가리키면 그 서브넷은 퍼블릭입니다. **이름은 태그고, 실체는 라우팅 테이블입니다.**

반대 방향도 성립합니다. 보안 그룹을 전부 열어도 IGW로 가는 경로가 없으면 인터넷에서 도달할 수 없습니다. 보안 그룹은 "통과시킬까 말까"를 판단하는 규칙이고, 라우팅 테이블은 **길이 있는가 없는가**입니다.

## 2. 구조

### 2-1. 라우트 — 목적지와 타깃

| 칸 | 의미 | 예 |
|---|---|---|
| 목적지 | 이 규칙이 담당하는 IP 범위. CIDR 또는 프리픽스 리스트 | `0.0.0.0/0`, `10.20.0.0/16`, `pl-xxxxxxxx` |
| 타깃 | 거기로 보낼 때 통과할 출구 | `local`, `igw-`, `nat-`, `pcx-`, `vgw-`, `tgw-`, `eni-`, `vpce-` |

라우팅 테이블이 판단에 쓰는 정보는 **목적지 IP 하나뿐**입니다. 포트도, 프로토콜도, 출발지 IP도 보지 않습니다. 그건 보안 그룹과 네트워크 ACL의 일입니다. 셋을 헷갈리면 디버깅이 산으로 갑니다.

### 2-2. local 라우트

모든 라우팅 테이블에는 VPC 내부 통신을 위한 `local` 라우트가 자동으로 들어갑니다. VPC에 IPv4 CIDR이 여러 개면 **CIDR마다 하나씩** 생기고, IPv6 CIDR을 붙였다면 IPv6용 local 라우트도 따로 생깁니다.

여기서 중요한 규칙 두 가지입니다.

- **IPv4와 IPv6는 완전히 별개로 계산됩니다.** `0.0.0.0/0` 라우트는 IPv6 트래픽을 전혀 커버하지 않습니다. IPv6를 쓰려면 `::/0` 라우트를 따로 만들어야 합니다. IPv6 CIDR만 붙여두고 라우트를 안 만들어서 "IPv6가 안 나간다"고 하는 경우가 이겁니다.
- **local보다 더 구체적인 라우트를 추가할 수 있습니다.** 단 조건이 붙습니다. 목적지는 VPC 안에 있는 **어떤 서브넷의 CIDR 전체와 정확히 일치**해야 하고, 타깃은 NAT 게이트웨이·네트워크 인터페이스·Gateway Load Balancer 엔드포인트 중 하나여야 합니다. 방화벽 어플라이언스를 서브넷 사이에 끼워 넣을 때 쓰는 장치입니다.

추가할 수 없는 대역도 있습니다. `169.254.168.0/22`(IPv4)와 `fd00:ec2::/32`(IPv6)는 AWS가 예약한 링크 로컬 대역이라 정확히 일치하거나 부분집합인 라우트를 만들 수 없습니다. EC2의 인스턴스 메타데이터 서비스(IMDS)와 DNS 서버가 이 대역을 씁니다. 더 큰 대역으로 덮어쓰는 건 가능하지만, **그래도 이 범위로 가는 패킷은 전달되지 않습니다.**

### 2-3. 메인 라우팅 테이블과 연결(association)

VPC를 만들면 **메인 라우팅 테이블**이 자동으로 하나 생깁니다. 규칙은 이렇습니다.

- 각 서브넷은 **반드시 라우팅 테이블 하나와 연결**됩니다. 명시적으로 연결하지 않으면 **메인 라우팅 테이블에 암묵적으로 연결**됩니다.
- 서브넷 하나는 동시에 **하나의** 라우팅 테이블만 가집니다. 반대로 테이블 하나를 여러 서브넷이 공유하는 건 됩니다.
- 메인 라우팅 테이블은 **삭제할 수 없습니다.** 커스텀 테이블은 연결이 하나도 없을 때만 삭제됩니다.
- 기본 VPC가 아닌 VPC를 직접 만들면 메인 라우팅 테이블에는 처음에 `local` 라우트만 들어 있습니다.

AWS 문서가 권하는 운영 방식은 **메인 라우팅 테이블을 기본 상태(local만) 그대로 두고, 새로 만드는 서브넷을 전부 커스텀 테이블에 명시적으로 연결하는 것**입니다. 이유는 5절에서 코드로 봅니다.

### 2-4. 확장 지점 — 게이트웨이 라우팅 테이블

라우팅 테이블은 서브넷뿐 아니라 **인터넷 게이트웨이나 가상 프라이빗 게이트웨이에도 연결**할 수 있습니다. 이걸 게이트웨이 라우팅 테이블, 이 연결을 엣지 연결(edge association)이라고 부릅니다. VPC로 **들어오는** 트래픽을 검사 어플라이언스로 먼저 보낼 때 씁니다.

제약이 빡빡합니다. 타깃은 `local`, Gateway Load Balancer 엔드포인트, 네트워크 인터페이스 셋뿐입니다. 목적지도 VPC CIDR 범위 밖으로는 못 씁니다. 프리픽스 리스트도 목적지로 못 씁니다. 라우트 전파가 켜진 테이블은 게이트웨이에 연결할 수 없고, 게이트웨이 라우팅 테이블을 메인으로 지정할 수도 없습니다. 그리고 **비대칭 라우팅은 지원되지 않습니다** — 돌아오는 트래픽도 같은 어플라이언스를 지나야 합니다.

## 3. 흐름

### 3-1. 우선순위 — 어떤 규칙이 이기는가

여러 라우트가 동시에 매칭되면 AWS는 다음 순서로 하나를 고릅니다.

```text
1. 가장 긴 프리픽스 (10.20.2.15/32 가 10.20.0.0/16 을 이깁니다)
2. 정적 라우트   (IGW, NAT GW, ENI, 인스턴스 ID, 게이트웨이 엔드포인트,
                  Transit Gateway, VPC 피어링, GWLB 엔드포인트)
3. 프리픽스 리스트를 참조하는 라우트
4. 전파된(propagated) 라우트
   4-1. Direct Connect BGP 라우트
   4-2. VPN 정적 라우트
   4-3. VPN BGP 라우트
```

2~4번은 **목적지 CIDR이 완전히 같을 때만** 따집니다. 프리픽스 길이가 다르면 무조건 1번이 먼저입니다. 프리픽스 리스트끼리 CIDR이 겹치면서 타깃이 다르면 AWS가 임의로 하나를 고르고, 그 뒤로는 계속 같은 것을 씁니다. 즉 **예측 가능하지 않으니 겹치게 만들지 않는 게 맞습니다.**

### 3-2. 판단 따라가기

프라이빗 서브넷에 이런 테이블이 붙어 있다고 하겠습니다.

| 목적지 | 타깃 | 전파됨 |
|---|---|---|
| `10.20.0.0/16` | `local` | No |
| `10.30.0.0/16` | `pcx-1a2b3c4d5e6f70890` | No |
| `pl-1a2b3c4d` (S3 프리픽스 리스트) | `vpce-1a2b3c4d5e6f70890` | No |
| `0.0.0.0/0` | `nat-1a2b3c4d5e6f70890` | No |

패킷의 목적지에 따라 이렇게 갈립니다.

```text
10.20.64.13   → local     : 같은 VPC 안. 라우터를 통해 다른 서브넷으로
10.30.5.7     → pcx-...   : 피어링된 VPC. /16 이 0.0.0.0/0 보다 구체적이라 이깁니다
S3 엔드포인트 IP → vpce-...  : 프리픽스 리스트가 0.0.0.0/0 보다 구체적입니다
1.2.3.4       → nat-...   : 나머지 전부. NAT를 거쳐 나갑니다
```

여기에 IGW 라우트는 한 줄도 없습니다. 그래서 이 서브넷은 프라이빗입니다.

한 가지 덜 알려진 규칙이 있습니다. AWS 문서는 **라우팅 테이블 규칙이 "서브넷을 떠나는 트래픽"에만 적용된다**고 정의합니다. 여기서 서브넷을 떠나는 트래픽이란 서브넷 라우터의 MAC 주소로 향하는 트래픽을 말합니다. 같은 서브넷 안의 다른 네트워크 인터페이스 MAC으로 직접 가는 트래픽은 L2로 처리되므로 라우팅 규칙이 적용되지 않습니다. 같은 서브넷에 어플라이언스를 두고 트래픽을 강제로 통과시키려는 설계가 실패하는 이유입니다.

### 3-3. 코드로 보는 구성

```hcl
resource "aws_vpc" "service" {
  cidr_block = "10.20.0.0/16"
  tags       = { Name = "service-stg" }
}

resource "aws_internet_gateway" "service" {
  vpc_id = aws_vpc.service.id
}

# 퍼블릭용 — 이 테이블의 igw 라우트 한 줄이 퍼블릭을 만듭니다
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.service.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.service.id
  }

  tags = { Name = "rtb-public" }
}

# 앱용 — AZ마다 하나. NAT가 AZ마다 있으므로 테이블도 갈라집니다
resource "aws_route_table" "app" {
  count  = 2
  vpc_id = aws_vpc.service.id

  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.service[count.index].id
  }

  tags = { Name = "rtb-app-${count.index}" }
}

# DB용 — local 라우트만. 밖으로 나가는 경로가 아예 없습니다
resource "aws_route_table" "db" {
  vpc_id = aws_vpc.service.id
  tags   = { Name = "rtb-db" }
}

resource "aws_route_table_association" "app" {
  count          = 2
  subnet_id      = aws_subnet.app[count.index].id
  route_table_id = aws_route_table.app[count.index].id
}
```

`aws_route_table.db`에는 `route` 블록이 하나도 없습니다. **비어 있는 게 설계입니다.** local 라우트는 AWS가 자동으로 넣어주므로 같은 VPC 안 통신은 되고, 그 밖으로는 나갈 수 없습니다.

## 4. 특징

### 4-1. 라우팅 테이블이 할 수 있는 것

- **경로의 유무로 경계를 만듭니다.** 규칙 검사가 아니라 길의 존재 여부이므로, 실수로 "허용"될 수 없습니다.
- **서브넷 단위로 정책을 재사용합니다.** 같은 성격의 서브넷 열 개가 테이블 하나를 공유해도 됩니다.
- **트래픽을 우회시킵니다.** 특정 대역만 피어링으로, 나머지는 NAT로 같은 분기가 목적지 IP 기준으로 가능합니다.

### 4-2. 할 수 없는 것

| 못 하는 것 | 대신 쓰는 것 |
|---|---|
| 포트·프로토콜별 제어 | 보안 그룹, 네트워크 ACL |
| 출발지 IP 기준 제어 | 보안 그룹, 네트워크 ACL |
| 같은 서브넷 안 인스턴스별 차등 경로 | 서브넷을 나눔 |
| 도메인 이름 기준 라우팅 | Route 53, 프록시 |

**인스턴스 하나만 인터넷에 내보내고 싶다**는 요구는 라우팅 테이블로 못 풉니다. 라우팅은 서브넷 단위이기 때문입니다. 그 인스턴스만 별도 서브넷으로 옮기는 게 정석입니다.

### 4-3. 트레이드오프

라우팅 테이블은 **상태가 아니라 그래프**입니다. 테이블 수가 늘면 "이 패킷이 어디로 가는가"를 사람이 머릿속으로 추적해야 하고, AZ 2개 × 계층 3개면 이미 테이블이 5~6개입니다. 여기에 피어링·Transit Gateway·엔드포인트가 붙으면 라우트가 수십 줄이 됩니다. **비용은 없지만 인지 부하는 확실히 있습니다.**

## 5. 예제 — 메인 라우팅 테이블을 어떻게 다루는가

### 5-1. 흔한 구성 ❌

```hcl
# ❌ 메인 라우팅 테이블에 인터넷 경로를 넣고, 서브넷 연결은 생략
resource "aws_default_route_table" "main" {
  default_route_table_id = aws_vpc.service.default_route_table_id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.service.id
  }
}

resource "aws_subnet" "batch" {
  vpc_id     = aws_vpc.service.id
  cidr_block = "10.20.160.0/24"
  # route_table_association 없음
}
```

동작은 합니다. 그래서 더 위험합니다.

몇 달 뒤 누군가 배치 작업용 서브넷을 하나 더 만듭니다. 라우팅 테이블 연결을 깜빡합니다. **그 서브넷은 조용히 메인 라우팅 테이블에 붙고, 곧바로 퍼블릭 서브넷이 됩니다.** 에러도, 경고도 없습니다. 여기에 DB를 올리면 IGW로 가는 경로를 가진 서브넷 안의 DB가 됩니다.

기본값이 "인터넷으로 나가는 것"이면, 실수의 결과가 항상 노출 쪽으로 기웁니다.

### 5-2. 개선한 구성 ✔️

```hcl
# ✅ 메인은 local 라우트만 남기고 아무 경로도 주지 않습니다
resource "aws_default_route_table" "main" {
  default_route_table_id = aws_vpc.service.default_route_table_id
  tags                   = { Name = "rtb-main-DO-NOT-USE" }
  # route 블록 없음 = 실수로 붙은 서브넷은 격리됩니다
}

resource "aws_subnet" "batch" {
  vpc_id     = aws_vpc.service.id
  cidr_block = "10.20.160.0/24"
}

resource "aws_route_table_association" "batch" {
  subnet_id      = aws_subnet.batch.id
  route_table_id = aws_route_table.app[0].id  # 명시적으로 선언
}
```

연결을 깜빡하면 이제 **서브넷이 격리됩니다.** 통신이 안 되니 즉시 발견되고, 발견되는 실수는 사고가 아닙니다. 노출되는 실수는 6개월 뒤에 발견됩니다.

메인 라우팅 테이블을 교체해야 한다면 AWS 문서가 권하는 순서가 있습니다. **먼저 커스텀 테이블을 만들어 서브넷 하나에 명시적으로 연결해 검증하고, 그다음 메인으로 승격**합니다. 메인을 직접 고치면 그 VPC의 암묵적 연결 서브넷 전부가 한 번에 영향을 받습니다.

## 6. 실무에서 찾아보는 라우팅 테이블

**게이트웨이 VPC 엔드포인트(S3·DynamoDB)** 는 라우팅 테이블에 직접 개입합니다. 엔드포인트를 만들면서 라우팅 테이블을 선택하면 AWS가 **해당 서비스로 향하는 라우트를 자동으로 추가**하고, 연결을 해제하면 그 라우트를 자동으로 제거합니다. 엔드포인트를 삭제해도 서브넷 라우팅 테이블에서 라우트가 사라집니다. 목적지 칸에 CIDR 대신 AWS 관리형 프리픽스 리스트(`pl-`로 시작)가 들어가는 것도 이때입니다.

여기서 자주 나오는 증상이 하나 있습니다. **엔드포인트를 만드는 순간 S3로 가는 기존 TCP 연결이 끊깁니다.** 소스 IP가 공인 주소에서 VPC 사설 주소로 바뀌기 때문입니다. AWS도 문서에서 중요한 작업이 도는 중에는 엔드포인트를 만들거나 수정하지 말라고 안내합니다.

**VPC 피어링**도 라우팅 테이블이 실체입니다. 피어링 연결을 수락하는 것만으로는 아무 통신도 되지 않습니다. **양쪽 VPC의 라우팅 테이블에 각각 상대 CIDR을 가리키는 라우트를 넣어야** 합니다. 한쪽만 넣으면 패킷은 나가는데 응답이 못 돌아옵니다.

## 7. 함정

### 함정 1 — NAT 게이트웨이를 지웠더니 라우트가 blackhole로 남습니다

- **증상**: 비용을 줄이려고 NAT 게이트웨이를 삭제했습니다. 그 뒤 프라이빗 서브넷의 애플리케이션이 외부 API 호출에서 타임아웃만 냅니다. 라우팅 테이블을 열어 보면 `0.0.0.0/0` 라우트가 남아 있는데 상태가 `blackhole`입니다.
- **원인**: **NAT 게이트웨이를 삭제해도 그 게이트웨이를 가리키던 라우트는 지워지지 않습니다.** AWS 문서가 명시합니다. 타깃이 사라진 라우트는 `blackhole` 상태가 되고, 이 라우트도 라우팅 판단에는 그대로 참여합니다. 즉 패킷은 이 규칙에 매칭되어 아무 데도 안 가고 버려집니다. "경로가 없다"가 아니라 "잘못된 경로가 있다"라서 더 헷갈립니다.
- **해법**: NAT 게이트웨이나 피어링, VGW를 삭제하는 작업은 **라우트 정리까지가 한 세트**입니다. 인프라 코드로 관리하면 타깃 리소스가 사라질 때 라우트도 함께 사라지므로 이 문제가 구조적으로 안 생깁니다. 콘솔에서 급하게 지웠다면 라우팅 테이블에서 `blackhole` 상태를 직접 검색해 확인합니다. 같은 상태는 **피어링 연결이 아직 `pending-acceptance`일 때도** 나타납니다. 이때는 라우트를 지우는 게 아니라 상대방이 수락하면 자동으로 살아납니다.

### 함정 2 — NAT 라우트를 잘못된 서브넷에 넣어 루프를 만듭니다

- **증상**: NAT 게이트웨이를 만들고 라우트도 넣었는데 프라이빗 서브넷에서 외부로 못 나갑니다. NAT 게이트웨이 자체는 `Available`입니다.
- **원인**: NAT 게이트웨이가 있는 **퍼블릭 서브넷의** 라우팅 테이블에 `0.0.0.0/0 → nat-xxx`를 넣은 경우입니다. NAT 게이트웨이는 자기가 나가려고 할 때도 자신이 속한 서브넷의 라우팅 테이블을 봅니다. 그 테이블이 다시 자신을 가리키면 패킷이 순환합니다. NAT는 **프라이빗 서브넷의 대리인이지, NAT가 있는 서브넷의 출구가 아닙니다.**
- **해법**: 라우트를 두 테이블에 나눠 넣습니다. **NAT가 있는 퍼블릭 서브넷의 테이블은 `0.0.0.0/0 → igw`**, **프라이빗 서브넷의 테이블이 `0.0.0.0/0 → nat`** 입니다. 3-3의 `aws_route_table.public`과 `aws_route_table.app`이 갈라져 있는 이유가 이겁니다.

### 함정 3 — Terraform에서 라우트가 매번 사라졌다 생겼다 합니다

- **증상**: `terraform plan`을 돌릴 때마다 라우트가 추가·삭제로 잡힙니다. 아무도 콘솔을 만지지 않았는데 그렇습니다. 배포 중 몇 초 동안 통신이 끊기기도 합니다.
- **원인**: `aws_route_table`의 인라인 `route` 블록과 별도 `aws_route` 리소스를 **같은 라우팅 테이블에 함께 쓴** 경우입니다. AWS 프로바이더 문서가 이를 명시적으로 금지합니다. 두 방식이 서로 상대의 규칙을 자기 상태에 없는 것으로 보고 덮어씁니다. 같은 문제가 게이트웨이 엔드포인트에서도 생깁니다. AWS가 자동으로 넣은 엔드포인트 라우트를 인라인 `route` 블록이 "내가 모르는 규칙"으로 보고 지웁니다.
- **해법**: 라우팅 테이블 하나에는 **한 가지 방식만** 씁니다. 게이트웨이 엔드포인트를 붙일 테이블이라면 인라인 블록을 쓰지 말고 `aws_route`로 통일하는 쪽이 안전합니다.

### 함정 4 — 서브넷은 나눴는데 라우팅 테이블을 공유하고 있습니다

- **증상**: `app-a`(AZ-a)와 `app-c`(AZ-c) 서브넷이 라우팅 테이블 하나를 공유합니다. AZ-a에 장애가 나자 AZ-c의 앱까지 외부 호출이 끊깁니다. 평소 청구서에도 AZ 간 데이터 전송 요금이 잡힙니다.
- **원인**: 라우팅 테이블 하나에는 `0.0.0.0/0` 라우트를 **하나만** 넣을 수 있습니다. 두 AZ가 같은 테이블을 쓰면 두 AZ의 아웃바운드가 같은 NAT 게이트웨이 하나를 통과합니다. NAT는 AZ에 속한 리소스이므로, 그 AZ가 죽으면 반대편 AZ의 트래픽도 함께 죽습니다.
<!-- TODO: AZ 간 데이터 전송 요금이 붙는다는 것까지는 확실하지만, NAT를 공유했을 때 실제로 얼마나 더 나오는지는 리전별 단가 확인이 필요합니다. 확인 전까지 수치를 쓰지 않았습니다. -->

- **해법**: **NAT 게이트웨이를 AZ마다 두고, 라우팅 테이블도 AZ마다 나눕니다.** 3-3에서 `aws_route_table.app`에 `count = 2`가 붙은 이유입니다. 비용을 아끼려고 NAT를 하나만 둘 거라면, 그건 가용성을 포기하는 의식적 선택이어야 합니다. 모르고 그렇게 되어 있는 것과는 다릅니다.

### 함정 5 — 라우트가 500개에서 막힙니다

- **증상**: Transit Gateway로 VPC를 계속 붙이다가 라우트 추가가 거부됩니다.
- **원인**: **라우팅 테이블당 비전파 라우트 기본 한도가 500개**입니다. 1,000개까지 올릴 수 있지만 AWS가 네트워크 성능 저하 가능성을 함께 안내합니다. 전파된 라우트는 **테이블당 100개이고 이 값은 조정되지 않습니다.**
- **해법**: 개별 프리픽스를 나열하는 대신 **요약 라우트를 광고**합니다(AWS 문서도 프리픽스가 더 필요하면 기본 라우트를 광고하라고 안내합니다). 자주 같이 쓰는 CIDR 묶음은 고객 관리형 프리픽스 리스트로 만들어 한 줄로 참조합니다. 다만 프리픽스 리스트를 참조하면 **그 리스트의 최대 엔트리 수만큼 한도를 차지**하므로, 최대 엔트리 수를 필요 이상으로 크게 잡지 않는 게 중요합니다.
