# 인덱스 없는 테이블은 왜 느린가

## 1. 핵심 개념: 인덱스란 무엇인가

- 인덱스는 책의 **찾아보기**와 같습니다. 특정 단어를 찾을 때 첫 페이지부터 넘기지 않고, 찾아보기에서 페이지 번호를 먼저 확인합니다.
- 데이터베이스도 마찬가지입니다. 인덱스가 없으면 조건에 맞는 행을 찾기 위해 테이블 전체를 처음부터 끝까지 읽습니다. 이걸 **풀 테이블 스캔**이라고 부릅니다.

> **테이블이 작을 때는 인덱스가 없어도 체감 차이가 없습니다.** 실무 데이터는 수백만, 수억 건까지 쌓이는데, 데이터가 어느 순간을 넘기면 똑같던 쿼리가 갑자기 느려집니다. 원인을 못 찾고 서버 사양만 올리는 경우가 흔합니다.

## 2. 구조

- **풀 테이블 스캔**: 조건에 맞는 행을 찾기 위해 테이블의 모든 행을 순서대로 확인합니다. 행이 N개면 최악의 경우 N번 확인해야 합니다.
- **인덱스를 통한 접근**: 인덱스는 컬럼 값과 그 값이 저장된 위치를 미리 정렬된 구조로 따로 보관합니다. 전체를 뒤지지 않고 원하는 값이 있는 위치로 바로 찾아갑니다. (내부 구조인 B-Tree는 `01-btree-index`에서 다룹니다.)

### 2-1. 선택적 확장 지점

- 기본 동작은 옵티마이저가 테이블 통계를 보고 인덱스를 쓸지 풀 스캔을 할지 자동으로 판단하는 것입니다.
- MySQL은 `FORCE INDEX`로 특정 인덱스를 쓰도록 강제할 수 있습니다. 옵티마이저 판단이 틀렸다고 확인했을 때만 선택적으로 씁니다.

## 3. 흐름

### 3-1. 예제 테이블과 쿼리

```sql
-- orders: id, customer_id, status, created_at (100만 건)
SELECT * FROM orders WHERE status = 'PENDING';
```

`status`에 인덱스가 없으면, 이 쿼리는 100만 행을 전부 읽으면서 `status` 값을 확인합니다.

### 3-2. 스캔 비용 흐름

```
전체 100만 행 중 status = 'PENDING'인 행은 1000건

풀 테이블 스캔: 100만 번 비교 (원하는 건 1000건뿐인데 전부 읽음)
인덱스 스캔:   'PENDING' 위치를 바로 찾아 1000건만 읽음
```

## 4. 특징

### 4-1. 사용 시기

- `WHERE`, `JOIN`, `ORDER BY` 절에 자주 등장하는 컬럼에 필요합니다.
- 값의 다양성(카디널리티)이 높은 컬럼일수록 효과가 큽니다. `status`처럼 값 종류가 몇 개 안 되는 컬럼은 인덱스 효과가 떨어질 수 있습니다.

### 4-2. 장점

- 탐색 비용을 테이블 전체를 읽는 것보다 훨씬 적은 비용으로 줄여줍니다. (구체적인 구조와 복잡도는 `01-btree-index` 참고)

### 4-3. 단점 / 트레이드오프

- 인덱스도 별도의 자료구조라 저장 공간을 씁니다.
- `INSERT`/`UPDATE`/`DELETE`할 때마다 인덱스도 같이 갱신해야 해서 쓰기 성능이 떨어집니다.
- 조회해야 할 데이터 비율이 높으면, 인덱스로 하나씩 찾아가는 것보다 순서대로 다 읽는 게 더 빠를 수 있습니다. (9장 참고)

## 5. 예제: 인덱스 없는 쿼리 VS 있는 쿼리

### 5-1. 클린하지 않은 코드 ❌

```sql
-- ❌ status 컬럼에 인덱스가 없으면 매번 테이블 전체를 읽는다
SELECT * FROM orders WHERE status = 'PENDING';
```

### 5-2. 인덱스를 생성한 코드 ✔️

```sql
-- ✅ status 컬럼에 인덱스를 만들면 옵티마이저가 이를 활용해 필요한 행만 찾는다
CREATE INDEX idx_orders_status ON orders (status);

SELECT * FROM orders WHERE status = 'PENDING';
```

## 6. 선택적 인덱싱 원칙

- 인덱스는 "일단 다 걸어두면 좋은 것"이 아닙니다. 실제로 조회 조건에 쓰이는 컬럼에만 선택적으로 걸어야 합니다.

### 6-1. 원칙을 어긴 코드 ❌

```sql
-- ❌ 조회 조건으로 쓴 적 없는 컬럼까지 전부 인덱스
CREATE INDEX idx_orders_created_at ON orders (created_at);
CREATE INDEX idx_orders_memo ON orders (memo);
```

### 6-2. 원칙을 지킨 코드 ✔️

```sql
-- ✅ WHERE/JOIN에 실제로 쓰이는 컬럼만 인덱스로 만든다
CREATE INDEX idx_orders_status ON orders (status);
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
```

## 7. 확장 지점 응용하기 — FORCE INDEX

### 7-1. 클린하지 않은 코드 ❌

```sql
-- ❌ 옵티마이저가 (부정확한 통계 등으로) 풀 스캔을 선택했지만, 실제로는 인덱스가 더 빠른 상황
SELECT * FROM orders WHERE customer_id = 12345;
```

### 7-2. FORCE INDEX를 적용한 코드 ✔️

```sql
-- ✅ 옵티마이저 판단이 틀렸다고 EXPLAIN으로 확인한 뒤 인덱스 사용을 강제한다
SELECT * FROM orders FORCE INDEX (idx_orders_customer_id)
WHERE customer_id = 12345;
```

- 항상 쓰면 옵티마이저의 정상적인 최적화를 막습니다. 실측 후에만 씁니다.

## 8. 실무에서 찾아보는 인덱스

- `EXPLAIN` — 쿼리가 인덱스를 타는지, 풀 스캔을 하는지 실행계획으로 보여주는 표준 도구입니다.
- Primary Key — 테이블에 PK를 지정하면 MySQL InnoDB를 포함한 대부분의 DB가 자동으로 인덱스를 만듭니다. 그 외 컬럼은 명시적으로 `CREATE INDEX`를 해야 인덱스가 생깁니다.

## 9. 관련된 개념과 비교

### 9-1. 풀 테이블 스캔 VS 인덱스 스캔

**유사점**

- 둘 다 "조건에 맞는 행을 찾는다"는 목적은 같습니다.

**차이점**

- 풀 테이블 스캔은 순차 접근이라 디스크 I/O 패턴이 예측 가능하고 일정합니다.
- 인덱스 스캔은 필요한 위치로 바로 찾아가는 대신, 흩어진 위치를 임의 접근(랜덤 I/O)해야 합니다.
- 조회할 데이터가 테이블의 일부(적은 비율)일 때는 인덱스가 유리하지만, 상당 부분을 읽어야 한다면 오히려 풀 스캔이 유리해지는 지점이 있습니다. 이 경계를 흔히 **손익분기점**이라 부릅니다.

## 10. 함정

**"인덱스를 걸면 무조건 빠르다"는 오해**

- **증상**: 인덱스를 만들었는데도 쿼리가 여전히 느리거나, `EXPLAIN`을 보면 옵티마이저가 인덱스를 무시하고 풀 스캔을 선택합니다.
- **원인**: 조회하는 행의 비율이 손익분기점을 넘으면, 인덱스로 하나씩 찾아가는 임의 접근이 오히려 순차로 다 읽는 것보다 느립니다. 옵티마이저는 이를 감안해 일부러 풀 스캔을 선택합니다.
- **해법**: 인덱스가 있다고 안심하지 말고 `EXPLAIN`으로 실제 실행계획을 확인합니다. (`05-index-not-used`에서 더 자세히 다룹니다.)

**"PK가 있으니 다른 컬럼도 자동으로 인덱스가 있을 것"이라는 착각**

- **증상**: `WHERE status = 'PENDING'` 같은 조건이 느린데, 테이블에 PK는 있으니 인덱스가 있을 거라 생각하고 넘어갑니다.
- **원인**: PK에는 자동으로 인덱스가 생기지만, 그 외 컬럼은 명시적으로 `CREATE INDEX`를 해야만 인덱스가 생깁니다.
- **해법**: `WHERE`/`JOIN`/`ORDER BY`에 자주 쓰이는 컬럼을 확인하고, 필요한 만큼만 직접 인덱스를 생성합니다.
