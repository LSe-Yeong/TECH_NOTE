# 대시보드는 무엇에 답해야 하는가

## 1. 핵심 개념

대시보드는 지표를 모아 놓은 벽이 아니라, **정해진 질문 하나에 즉시 답하는 화면**입니다. Grafana 공식 문서는 대시보드를 만들 때 가장 먼저 할 일로 "이 대시보드가 답할 질문 또는 들려줄 이야기"를 정하라고 말합니다. 목표가 없으면 그 대시보드가 필요한지부터 의심하라고도 덧붙입니다.

> 장애가 터졌는데 패널 40개를 스크롤하며 "어디 보면 되지"를 찾는 순간, 그 대시보드는 모니터링 도구가 아니라 대응 시간을 늘리는 장치입니다. 그리고 보통 대시보드는 그런 상태로 만들어집니다 — 질문에서 출발하지 않고, 수집된 지표에서 출발했기 때문입니다.

이 문서가 답할 질문은 하나입니다. **왜 내 대시보드는 장애 때 답하지 못하고, 무엇을 바꿔야 답하게 되는가.** 무엇을 측정할지는 다루지 않습니다(`daily/day54-golden-signals.md`). 여기서는 측정된 것을 어떻게 배치하고 어디서 신뢰를 잃는지를 봅니다.

Grafana 관련 설명은 공식 문서 `latest`(v13.x 문서와 동일 내용, 2026년 11월 확인) 기준입니다.

---

## 2. 증상 — 쓸모없어진 대시보드의 네 가지 모습

**증상 1. 장애 때 아무도 안 봅니다.** 슬랙에 "CPU 좀 봐주세요"가 올라오고, 사람들은 대시보드 대신 서버에 SSH로 들어갑니다. 대시보드가 있는데 평소 쓰지 않으니 급할 때 어디에 뭐가 있는지 모릅니다.

**증상 2. 전부 초록인데 사용자는 못 씁니다.** 평균 응답시간 120ms, 에러율 0.3%, CPU 40%. 그런데 특정 엔드포인트 하나가 전부 타임아웃입니다. 집계값이 소수의 실패를 희석했습니다.

**증상 3. 같은 대시보드가 12개입니다.** `API 모니터링`, `API 모니터링 v2`, `API 모니터링 (김OO)`, `API 모니터링-복사`. 검색하면 다 나오는데 어느 게 최신인지 아무도 모릅니다. Grafana 문서는 이걸 **dashboard sprawl**이라고 부르고, 가장 큰 피해는 "맞는 대시보드를 찾는 시간"이라고 지적합니다.

**증상 4. 그래프의 숫자가 실제 숫자와 다릅니다.** 같은 패널을 크게 열면 피크가 더 높게 보입니다. 시간 범위를 3시간으로 줄이면 그래프가 비어버립니다. 이건 데이터 문제가 아니라 대시보드 설정 문제인데, 설정 문제라는 걸 모르면 지표 자체를 못 믿게 됩니다.

네 증상의 원인은 각각 다릅니다. 하나씩 봅니다.

---

## 3. 원인 1 — 질문 없이, 지표에서 출발했습니다

지표에서 출발하면 대시보드는 이렇게 생깁니다.

```
[CPU] [Memory] [Disk] [Network In] [Network Out]
[JVM Heap] [GC Count] [Thread Count] [Open FD]
[HTTP 요청 수] [평균 응답시간] [2xx] [4xx] [5xx]
...
```

전부 유용한 지표입니다. 그런데 이 화면은 어떤 질문에도 답하지 않습니다. "지금 사용자가 아픈가?"에 답하려면 `5xx`와 지연시간을 봐야 하는데 열한 번째 패널에 있고, `CPU`와 나란히 놓여 있어서 둘 중 뭐가 증상이고 뭐가 원인인지 화면이 알려주지 않습니다.

질문에서 출발하면 질문 자체가 계층을 만듭니다.

1. **지금 사용자가 아픈가** — 증상. 한 화면, 스크롤 없음.
2. **어디가 아픈가** — 서비스·엔드포인트·AZ 중 어디로 좁혀지는가.
3. **왜 아픈가** — 진단. 자원, 의존성, 최근 변경.

Google SRE Workbook은 SLI 지표를 서비스 대시보드에서 **가장 눈에 띄는 곳, 가능하면 랜딩 페이지**에 두라고 권합니다. 그리고 중요한 단서를 하나 더 줍니다. SLO 대시보드는 SLO가 깨지고 있다는 것은 보여주지만 **왜 깨지는지는 보여주지 않으므로**, 진단용 대시보드를 알림에서 링크로 연결해 두라는 것입니다.

즉 1계층과 3계층은 **같은 화면에 있으면 안 됩니다.** 섞으면 1계층이 희석됩니다.

## 4. 원인 2 — 집계가 문제를 가립니다

증상 2의 원인입니다. 대시보드에서 숫자를 하나로 줄이는 모든 행위는 정보를 버립니다. 문제는 **무엇을 버렸는지 화면에 안 적힌다**는 점입니다.

**평균.** 요청 1000건 중 10건이 30초 걸리고 990건이 50ms면 평균은 약 348ms입니다. 그래프는 완만하게 올라가고, 10명은 서비스를 못 씁니다.

**인스턴스별 분위수의 평균.** 분위수는 합산도 평균도 되지 않습니다. 인스턴스 10대의 p99를 평균한 값은 어떤 사용자의 경험도 아닙니다. Prometheus에서는 `histogram_quantile`을 **합산한 히스토그램 위에서** 계산해야 합니다.

```promql
# ❌ 인스턴스별 p99를 평균 — 아무 의미 없는 숫자
avg(histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[$__rate_interval])))

# ✅ 버킷을 먼저 합산하고 그 위에서 분위수 계산
histogram_quantile(
  0.99,
  sum by (le) (rate(http_server_requests_seconds_bucket[$__rate_interval]))
)
```

**전체 합.** 에러율을 서비스 전체로 계산하면, 트래픽이 작은 엔드포인트가 100% 실패해도 소수점에 묻힙니다. 결제 API가 전체 트래픽의 0.5%라면 완전히 죽어도 전체 에러율은 0.5%입니다.

```promql
# ✅ 엔드포인트별로 쪼개서, 실패하는 것만 화면에 남긴다
topk(5,
  sum by (uri) (rate(http_server_requests_seconds_count{status=~"5.."}[$__rate_interval]))
  /
  sum by (uri) (rate(http_server_requests_seconds_count[$__rate_interval]))
)
```

Grafana 문서도 같은 방향을 권합니다. **크기(magnitude)가 다른 대상은 대시보드를 쪼개라** — 집계 지표가 중요한 정보를 묻어버리지 않게. 그리고 **문제가 있는 대상만 보여주라**고 합니다. 서버 200대를 다 그리면 아픈 1대를 못 찾습니다.

**스택 그래프.** Grafana 문서는 스택이 오해를 만들고 데이터를 가릴 수 있으니 **대부분의 경우 끄라**고 명시합니다. 스택에서는 각 계열의 값을 눈으로 읽을 수 없고, 맨 위 계열만 절대값으로 읽힙니다.

**정규화.** 자원 지표는 비율로 바꿔야 비교됩니다. CPU를 코어 수로 나눠 퍼센트로 두면 2코어 인스턴스와 16코어 인스턴스를 같은 패널에서 볼 수 있습니다.

## 5. 원인 3 — 그래프에 찍힌 숫자가 쿼리 결과가 아닙니다

여기가 증상 4의 원인이고, 대시보드에서 가장 조용히 사람을 속이는 지점입니다. Grafana는 쿼리를 그대로 던지지 않습니다. **패널 크기에 맞춰 해상도를 계산해서** 던집니다.

### 5-1. Max data points는 기본값이 패널의 픽셀 폭입니다

Grafana 문서에 따르면 **Max data points의 기본값은 패널의 픽셀 폭**입니다. 그래프가 표시할 수 있는 점의 개수가 그 정도이기 때문입니다. 쿼리가 이보다 많은 점을 반환하면 데이터소스가 평균이나 최대 등으로 **집계해서 개수를 줄입니다.**

결과가 두 가지입니다.

- **피크가 깎입니다.** 폭 400px 패널에서 24시간을 보면 점 하나가 약 3.6분입니다. 10초간 치솟은 스파이크는 3.6분 구간의 평균에 섞여 사라집니다.
- **같은 패널이 크기에 따라 다른 값을 보여줍니다.** 문서는 이걸 명시합니다 — 패널을 `v`로 전체 보기로 열면 픽셀이 늘어나 Grafana가 더 많은 점을 요청하므로 **해상도가 올라가고 점 사이 간격이 줄어듭니다.** 변환(transformation)·리듀서·expression으로 계산되는 값까지 바뀔 수 있다고 경고합니다.

그래서 **숫자를 읽어야 하는 패널은 Max data points를 고정값으로 박아야** 합니다. 문서가 권하는 해법도 "일관된 결과를 원하면 고정값을 설정하라"입니다.

### 5-2. `$__rate_interval`과 스크랩 간격

시간 범위를 줄였을 때 그래프가 비는 현상의 원인입니다.

`rate()`는 창 안에 **샘플이 최소 2개** 있어야 계산됩니다. 창이 스크랩 간격보다 짧으면 샘플이 1개 이하라 결과가 없습니다. Grafana 트러블슈팅 문서가 같은 사례를 듭니다 — 5분 간격으로 스크랩하는데 `[1m]`으로 물으면 데이터가 안 나옵니다.

`$__interval`은 **시간 범위와 패널 폭으로 계산**되므로, 범위를 줄이면 같이 줄어듭니다. `rate($__interval)`로 써 두면 범위를 좁힌 순간 창이 스크랩 간격 밑으로 내려가 그래프가 비어버립니다. 이걸 막기 위한 변수가 `$__rate_interval`입니다. 공식 정의는 이렇습니다.

```
$__rate_interval = max($__interval + scrape_interval, 4 * scrape_interval)
```

스크랩 샘플을 **최소 4개** 확보하도록 창을 넓히는 식입니다. 그런데 여기서 쓰는 `scrape_interval`은 Prometheus 서버에서 읽어오는 값이 **아닙니다.**

- 쿼리의 **Min step**이 설정돼 있으면 그 값
- 없으면 **데이터소스 설정의 Scrape interval**, 그리고 이 설정의 **기본값은 `15s`**

즉 Prometheus가 `scrape_interval: 60s`로 돌고 있는데 데이터소스를 손대지 않았다면, Grafana는 15초라고 믿고 창을 60초로 잡습니다. 60초 간격 데이터에 60초 창이면 샘플 2개가 간신히 걸리거나 안 걸립니다. 간헐적으로 비는 그래프의 전형적인 원인입니다.

```yaml
# ✅ 프로비저닝 파일에서 스크랩 간격을 Prometheus 설정과 맞춘다
apiVersion: 1
datasources:
  - name: Prometheus
    type: prometheus
    access: proxy
    url: http://prometheus.internal.example.com:9090
    jsonData:
      timeInterval: 60s   # prometheus.yml의 scrape_interval과 동일하게
      httpMethod: POST
```

문서가 덧붙이는 주의사항 둘. 패널의 **Min interval은 이 계산에 쓰이는 스크랩 간격을 바꾸지 않습니다**(Min step이 바꿉니다). 그리고 타깃마다 스크랩 간격이 다르면 **가장 긴 값**을 기준으로 잡아야 합니다.

## 6. 원인 4 — 대시보드가 번식합니다

Grafana 문서가 짚는 sprawl의 **가장 흔한 원인은 "하나만 바꾸려고 복제하는 것"**입니다. 인스턴스별로, 환경별로, 팀별로 복사하다 보면 원본의 수정이 복사본에 반영되지 않습니다.

해법은 복사 대신 **템플릿 변수와 URL 파라미터**입니다. 마스터 대시보드 하나에 변수를 두면 복제가 필요 없습니다. 데이터소스까지 변수로 두면 dev/prod를 같은 대시보드로 봅니다.

```json
{
  "templating": {
    "list": [
      {
        "name": "service",
        "type": "query",
        "datasource": "Prometheus",
        "query": "label_values(http_server_requests_seconds_count, service)",
        "refresh": 1,
        "includeAll": false
      }
    ]
  }
}
```

문서가 주는 운영 규칙들입니다.

- 주기적으로 리뷰해서 **안 쓰는 대시보드를 지웁니다.**
- 임시 대시보드는 이름에 **`TEST:` 접두사**를 붙이고 끝나면 삭제합니다.
- 꼭 복제해야 하면 **이름을 바꾸고 태그를 지웁니다.** 복사된 태그가 검색에서 오탐을 만듭니다.
- 대시보드 **JSON을 버전관리**합니다.
- 실험은 **별도 Grafana 인스턴스**에서 하고, 쓸모가 증명된 것만 프로덕션으로 옮깁니다.
- **불필요한 자동 갱신을 끕니다.** 시간당 바뀌는 데이터를 30초마다 새로 긁으면 네트워크와 백엔드에 부하만 줍니다.

## 7. 해법 — 질문의 계층을 대시보드의 계층으로 만듭니다

Grafana 문서는 **각 단계가 다음 단계로 링크되는 계층형 대시보드**를 권하고, 사용자가 검색으로 헤매게 두지 말고 링크와 템플릿 변수로 **이동 경로를 정해 주라**고 합니다. 그리고 **대부분의 대시보드는 알림에서 도달 가능해야 한다**고 못 박습니다.

흐름은 이렇게 됩니다.

```
알림(증상 기반) → ① 서비스 개요 → ② 컴포넌트/엔드포인트 → ③ 진단
```

**① 서비스 개요 — "지금 사용자가 아픈가"**

스크롤 없이 한 화면. SLI와 에러 예산 소진율을 맨 위에. 지연시간은 분위수로, 에러는 비율로. 패널은 적을수록 좋습니다. Grafana 문서의 예시 배치는 **서비스당 한 행, 데이터 흐름 순서대로, 왼쪽에 요청·에러율, 오른쪽에 지연시간**입니다. 순서를 고정하면 눈이 위치를 기억합니다.

**② 컴포넌트 — "어디가 아픈가"**

엔드포인트별·인스턴스별·AZ별로 쪼갠 화면. `topk`로 나쁜 것만 올립니다. 여기서 범위가 좁혀져야 ③으로 갈 수 있습니다.

**③ 진단 — "왜 아픈가"**

SRE Workbook이 권하는 대시보드 구성이 여기에 해당합니다.

- **의도된 변경** — 배포된 바이너리 버전, 커맨드라인 플래그, 동적 설정 버전
- **의존성 상태** — 의존 대상마다 요청/응답 크기, 지연시간, 응답 코드. 레이블로 응답 코드·RPC 메서드·상대 job 이름
- **포화도** — 서비스가 의존하는 모든 자원. JVM 힙·메타스페이스, Go 고루틴 수 같은 것까지. Workbook은 이 지표들이 **용량·자원 계획에 필수**라고 표현합니다
- **응답 코드별 트래픽 현황**

진단 계층에서 **"최근 변경" 패널이 제일 먼저 와야** 합니다. 장애 원인의 상당 부분은 방금 바꾼 것이고, 이걸 대시보드에서 1초에 확인할 수 있으면 조사 범위가 즉시 좁혀집니다.

**대상 사용자(audience)를 나눕니다.** Workbook은 경영진과 SRE가 서로 다른 뷰를 필요로 하고, 각 뷰 묶음 안에서는 **같은 종류의 데이터를 일관되게** 보여줘야 한다고 말합니다. 하나의 대시보드로 둘을 다 만족시키려는 시도가 "아무 질문에도 답하지 않는 화면"을 만듭니다.

## 8. 예제 — 같은 지표로 만든 두 개의 개요 대시보드

주문 API 하나를 모니터링하는 상황입니다. 수집되는 지표는 양쪽 다 같습니다.

### 8-1. 질문이 없는 대시보드 ❌

```
행 1: [평균 응답시간]  [총 요청 수]  [CPU 사용률(코어 수)]
행 2: [인스턴스별 메모리(스택)]  [GC 횟수]  [스레드 수]
행 3: [상태코드 분포(스택)]  [DB 커넥션 수]  [Redis 히트율]
행 4: ... (패널 11개 더)
기본 시간 범위: Last 6 hours / 자동 갱신: 10s
```

```promql
# ❌ 평균 — 소수의 느린 요청이 희석된다
avg(rate(http_server_requests_seconds_sum[$__interval]))
  / avg(rate(http_server_requests_seconds_count[$__interval]))
```

이 화면이 답하지 못하는 질문: *지금 사용자가 아픈가.* 에러는 3행 스택 그래프 안에 있어서 5xx만 따로 읽을 수 없고, 지연시간은 평균이라 꼬리가 보이지 않습니다. `$__interval`을 썼으니 시간 범위를 15분으로 줄이면 그래프가 빌 수 있습니다. 그리고 증상(지연·에러)과 원인 후보(CPU·GC·커넥션)가 같은 화면에 섞여 있어 어느 쪽이 먼저인지 화면이 알려주지 않습니다.

### 8-2. 질문에서 출발한 대시보드 ✔️

```
텍스트 패널: "주문 API — 지금 사용자가 아픈가?
             나쁘면 → [엔드포인트별 상세] [진단: 자원·의존성·배포]"

행 1 (증상, 스크롤 없음)
  [가용성 SLO 소진율]   [p99 지연시간]   [에러율 %]
행 2 (어디가)
  [에러율 상위 5개 엔드포인트]   [p99 상위 5개 엔드포인트]
행 3 (링크)
  [최근 배포 시각·버전]  → 진단 대시보드 링크

기본 시간 범위: Last 30 minutes / 자동 갱신: 30s
Max data points: 300 (고정)
```

```promql
# ✔️ 분위수는 버킷을 합산한 뒤 계산, 창은 $__rate_interval
histogram_quantile(
  0.99,
  sum by (le) (rate(http_server_requests_seconds_bucket{job="order-api"}[$__rate_interval]))
)
```

```promql
# ✔️ 에러는 비율로, 나쁜 엔드포인트만 올려서
topk(5,
  sum by (uri) (rate(http_server_requests_seconds_count{job="order-api", status=~"5.."}[$__rate_interval]))
  /
  sum by (uri) (rate(http_server_requests_seconds_count{job="order-api"}[$__rate_interval]))
)
```

바뀐 것은 지표가 아니라 **질문의 유무와 계층**입니다. 패널 수는 20개에서 7개로 줄었고, CPU·GC·커넥션은 사라진 게 아니라 진단 대시보드로 내려갔습니다. 2행에서 범위가 좁혀지고, 3행에서 "방금 배포했는가"가 즉시 확인됩니다.

## 9. 함정

**함정 1. 패널 설명이 비어 있습니다**

- **증상**: 새로 들어온 사람이 `job:slo_burn_rate:1h` 패널을 보고 이게 높으면 좋은 건지 나쁜 건지 모릅니다. 장애 중에 슬랙으로 물어봅니다.
- **원인**: 만든 사람의 머릿속에만 맥락이 있습니다. 대시보드는 코드와 달리 설명을 적는 관행이 없습니다.
- **해법**: 패널 description에 "무엇을 재는가 / 어느 값이 나쁜가 / 나쁘면 어디를 보는가"를 적습니다. 대시보드 상단에 텍스트 패널로 용도와 다음 단계 링크를 둡니다. Grafana 문서도 텍스트 패널과 패널 description으로 **대시보드를 문서화하라**고 권합니다. 임계값 색상(좋음/나쁨)을 쓰면 설명을 읽기 전에 판단됩니다.

**함정 2. 알림과 대시보드가 다른 쿼리를 씁니다**

- **증상**: 알림은 울렸는데 대시보드에서는 임계값을 안 넘습니다. 오탐으로 판단하고 닫았는데 실제 장애였습니다.
- **원인**: 알림 룰은 `rate(...[5m])` 고정 창을 쓰고, 대시보드는 `$__rate_interval`로 시간 범위에 따라 변하는 창을 씁니다. 두 숫자는 애초에 같을 수 없습니다. Max data points로 인한 다운샘플링까지 겹치면 차이가 더 벌어집니다.
- **해법**: 임계값을 판단하는 핵심 지표는 **기록 규칙(recording rule)으로 Prometheus 쪽에 한 번만 정의**하고, 알림과 대시보드가 **같은 이름을 참조**하게 합니다.

```yaml
# prometheus.yml이 로드하는 rule 파일
groups:
  - name: order-api-slo
    interval: 30s
    rules:
      - record: job:http_error_ratio:rate5m
        expr: |
          sum by (job) (rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          /
          sum by (job) (rate(http_server_requests_seconds_count[5m]))
```

**함정 3. 시간 범위 기본값이 `Last 6 hours`입니다**

- **증상**: 대시보드를 열면 평평한 선만 보입니다. 지금 진행 중인 급변이 6시간 그래프에서는 오른쪽 끝 한 픽셀입니다.
- **원인**: 기본 시간 범위가 대시보드의 용도와 안 맞습니다. 개요 대시보드는 "지금"을 보는 화면이고, 용량 계획 대시보드는 "몇 주"를 보는 화면인데 같은 기본값을 씁니다.
- **해법**: 대시보드별로 기본 시간 범위를 용도에 맞춰 저장합니다(개요는 15~30분, 추세는 7~30일). 알림에서 링크를 걸 때는 URL에 `from`/`to`를 넣어 **장애 시점이 화면 가운데 오도록** 고정합니다.

**함정 4. 쓰이지 않는 지표가 계속 쌓입니다**

- **증상**: 수집 비용은 늘어나는데 그 지표를 보는 대시보드도, 참조하는 알림도 없습니다.
- **원인**: "일단 넣어두면 나중에 쓸지도 모른다"로 계측했습니다.
- **해법**: SRE Workbook의 기준은 **"노출하는 모든 지표는 목적이 있어야 한다"**이고, 만들기 쉽다는 이유만으로 지표를 노출하지 말라고 합니다. 반대 방향 보강도 Workbook이 권합니다 — **포스트모템에서 "어떤 지표가 있었으면 진단이 빨랐을까"를 따져서** 그것만 추가합니다.
